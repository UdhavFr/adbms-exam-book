## Beats

1. **intro** — Title card: where logs undo death itself.
2. **ground** — Crash callback (ch20's transfer, power dies): two questions —
   undo the half-done? redo the committed-but-unsaved?
3. **deferred** — Log → execute (no DB write) → COMMIT → REDO into DB.
   Crash: REDO committed; uncommitted need no UNDO. "Deferred = Delay → REDO only."
4. **immediate** — Log old/new → data may hit disk early → COMMIT? YES→REDO / NO→UNDO.
   "Immediate = I need both."
5. **q1** — Q111: which scheme never needs UNDO → deferred.
6. **shadow** — Stable SHADOW table + changing CURRENT table → root flips at commit;
   crash before commit → shadow mapping. Trade-off: simple ↔ fragmentation.
   Trap: the shadow table is stable, never updated during execution.
7. **wal** — THE rule: log record reaches stable storage BEFORE the data page.
   Log record anatomy `<T1, A, 100, 50>`. No log-first → no undo/redo possible.
8. **checkpoint** — Bookmark in the log: recovery starts here, not at page one.
9. **q2** — Q112: WAL means… → log first, then data page.
10. **wrap** — Master flow (define→failures→deferred→immediate→shadow→log→WAL→
    checkpoint→UNDO/REDO) + THE single rule: committed = REDO, uncommitted = UNDO.
11. **final1** — Q133: WAL requires… → log record first, then changed page.
12. **final2** — custom QAC5: "Crash finds uncommitted changes on disk. Which scheme
    was running?" → immediate (deferred never lets them reach disk). Verified vs U3-10.
13. **final3** — custom QAC6: "Shadow paging recovers by…" → switching the root
    pointer (old mapping intact). Verified vs U3-11.
