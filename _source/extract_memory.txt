Heading 1 | UNIT 2 — NORMALIZATION, STORAGE & INDEXING
Heading 2 | 1. Functional dependency
Ultra | X → Y means X determines Y. X = determinant; Y = functionally dependent.
Rule | FD types: Trivial (Y⊆X) | Non-trivial (Y not⊆X) | Full | Partial | Transitive
Memory | Transitive: X→Y and Y→Z imply X→Z
Heading 2 | 2. Attribute closure
Memory | X+ = all attributes functionally determined by X.
Rule | ALGORITHM: Start with X → repeatedly add RHS of any FD whose LHS is already inside closure → stop when no new attributes → if X+ contains all attributes, X is a superkey.
Memory | MEMORY: Start → Unlock → Add → Repeat → Complete
Heading 2 | 3. NORMALIZATION LADDER — memorize this perfectly
Ultra | UNF → 1NF → 2NF → 3NF → BCNF → 4NF → 5NF
--- TABLE ---
NF | What it fixes / defining memory
1NF | Atomic values; no repeating groups/nested sets
2NF | 1NF + no partial dependency; non-prime attributes depend on whole candidate key
3NF | 2NF + no undesirable transitive dependency; X is superkey OR A is prime
BCNF | Every determinant of a non-trivial FD is a superkey
4NF | Every non-trivial MVD has a superkey determinant
5NF | Every non-trivial join dependency is implied by candidate keys
--- END TABLE ---
Memory | ONE-LINE MEMORY: 1=Atomic | 2=Partial | 3=Transitive | BCNF=Determinant | 4=MVD | 5=Join
Warning | 3NF = OR   |   BCNF = ONLY
Heading 2 | 4. The canonical examples
Rule | 2NF: ENROLL(StudentID, CourseID, StudentName, CourseName, Grade) with key (StudentID,CourseID); StudentID→StudentName and CourseID→CourseName are partial → decompose STUDENT / COURSE / ENROLL.
Rule | 3NF: EMPID→DeptID and DeptID→DeptName, therefore EMPID→DeptName transitively → separate DEPARTMENT.
Rule | 4NF: independent HOBBIES and LANGUAGES for same STUDENT → separate STUDENT_HOBBY and STUDENT_LANGUAGE.

Heading 2 | 10. Two-phase locking
Ultra | GROWING → LOCK POINT → SHRINKING
Memory | Growing: acquire, no release | Shrinking: release, no new acquisition
Rule | Basic 2PL → conflict serializability | Strict 2PL → hold X locks until commit/abort | Rigorous 2PL → hold S and X locks until completion
Heading 2 | 11. Deadlock
Memory | T1 holds A and waits B; T2 holds B and waits A → cycle = deadlock
Ultra | PADT = Prevention | Avoidance | Detection | Timeout
Heading 2 | 12. Timestamp ordering
Rule | Each transaction gets a timestamp; older = smaller timestamp. Read_TS(X)=largest successful read timestamp; Write_TS(X)=largest successful write timestamp. Violation may cause abort/restart.
Memory | Benefit: no lock waiting → avoids lock-based deadlocks | Cost: repeated aborts waste work

Heading 2 | 4. Replication vs allocation
Memory | Replication = multiple copies at multiple sites. Full = many/all sites; Partial = selected sites.
Memory | Replication BENEFITS: availability, local reads, failure tolerance, less remote access. COSTS: storage, update coordination, consistency, network/control overhead.
Memory | Allocation = which site stores which fragment/replica; consider query frequency, locality, communication cost, storage capacity, reliability.
Heading 2 | 5. Two-phase commit (2PC)
Ultra | PHASE 1: COORDINATOR → PREPARE → participants vote YES/NO
Ultra | PHASE 2: all required YES → COMMIT; otherwise → ABORT
Memory | MEMORY: ASK → VOTE → DECIDE
Memory | Limitation: can block when participants are prepared but cannot learn coordinator’s final decision.
Heading 2 | 6. Consistency models
Memory | Strong/linearizable-style | Eventual | Causal | Session-oriented (e.g. read-your-writes / monotonic reads)
Memory | Trade-off idea: stronger consistency can require more coordination and affect latency/availability during failures.
Heading 2 | 7. CAP — exact memory
Ultra | During a network partition, a distributed system cannot simultaneously guarantee BOTH strong consistency AND availability for every request under the formal CAP definitions.
--- TABLE ---
C | Consistency | Read observes most recent write according to formal guarantee, or error
A | Availability | Every request to a non-failing node gets a non-error response; value need not be latest
P | Partition tolerance | System continues despite network failures preventing node communication
--- END TABLE ---
Warning | DO NOT WRITE “pick any two at all times.” CAP is specifically about behavior when a partition occurs.
Heading 2 | 8. BASE

Memory | ACID = strong transaction-oriented guarantees | BASE = availability/flexible consistency emphasis
Heading 2 | 9. Sharding

Memory | Range = key ranges | Hash = hash(shard key) | Directory = mapping service | Geographic = by region
Memory | Good shard key: distributes data/traffic, supports common queries, avoids hotspots/oversized partitions.
