Heading 1 | UNIT 1 — DATABASE SYSTEM CONCEPTS AND CONCEPTUAL MODELING
Heading 2 | 1. Introduction to Database Systems
ExamText | A database is an organized collection of logically related data that represents information about a particular application or organization. A Database Management System (DBMS) is software that allows users and applications to define, create, store, retrieve, update, protect, and recover data in a controlled manner. The database together with the DBMS forms a database system.
ExamText | Examples of database applications include banking, railway and airline reservation, e-commerce, hospitals, universities, libraries, social networks, and financial systems. Modern systems may use relational DBMSs such as PostgreSQL and MySQL or NoSQL systems such as MongoDB, Cassandra, Redis, and Neo4j.
Heading 3 | Why DBMS is needed
ExamText | A traditional file-processing system stores information in separate application files. When the same customer information is stored in many files, duplication occurs. If one copy is changed and another is not, inconsistency appears. File systems also make sharing, security, backup, concurrent access, and recovery difficult.
--- TABLE ---

Data redundancy | Centralized/shared database design reduces unnecessary duplication.
Data inconsistency | Constraints and controlled updates keep related data consistent.
Difficult data sharing | Multiple users/applications can access a common database.
Security problems | Authentication and authorization mechanisms control access.
Concurrent access | Concurrency-control mechanisms coordinate simultaneous transactions.
Failure recovery | Logging, checkpoints and recovery mechanisms restore consistency.
Program-data dependence | Data abstraction and data independence reduce application dependence on physical storage.
--- END TABLE ---

Heading 2 | 3. Levels of Data Abstraction
ExamText | Database systems hide unnecessary implementation details from users through data abstraction. The classic three-level architecture separates user views, logical organization, and physical storage.

Heading 3 | External level
ExamText | The external level describes customized views for different users. A student may see courses and marks while an accounts employee sees fees and payments. Views improve simplicity and security.
Heading 3 | Conceptual level
ExamText | The conceptual level represents the complete logical structure independent of physical storage. It describes entities, attributes, relationships, constraints, and the logical organization of data.
Heading 3 | Internal level
ExamText | The internal level explains how data is physically represented, including files, pages, record placement, indexes, access paths, and storage structures.
Heading 3 | Data independence
ExamText | Physical data independence is the ability to change physical storage structures without changing the conceptual schema. For example, replacing one index structure with another should not require rewriting application queries.
ExamText | Logical data independence is the ability to modify the conceptual schema without requiring changes to every external view or application, as long as the required external information can still be provided.

Logical data independence | Logical schema can evolve while preserving required external views. | Split a table while maintaining a compatible view.

Heading 2 | 4. Conceptual Modeling Using ER Approach
ExamText | The Entity–Relationship (ER) approach is a high-level conceptual modeling technique used before implementing the database. It describes entities, their attributes, relationships, and constraints in a form that is easy to understand.
Heading 3 | Entities
ExamText | An entity is a distinguishable real-world object about which data is stored. Examples include STUDENT, EMPLOYEE, PRODUCT and DEPARTMENT. An entity set is a collection of similar entities.
Heading 3 | Attributes
List Bullet | Simple attribute: cannot be meaningfully divided further, such as Age.
List Bullet | Composite attribute: consists of components, such as Address containing Street, City and PIN.
List Bullet | Single-valued attribute: has one value for each entity.
List Bullet | Multivalued attribute: may contain several values, such as multiple phone numbers.
List Bullet | Derived attribute: calculated from other data, such as Age derived from DateOfBirth.
List Bullet | Key attribute: uniquely identifies an entity.

Heading 2 | 5. Mapping ER Diagrams to Relational Schemas
ExamText | ER-to-relational mapping transforms the conceptual ER design into tables suitable for a relational DBMS.
List Number | For each strong entity, create a relation containing its simple attributes. Select the entity's primary key as the relation's primary key.
List Number | For a composite attribute, store its individual components rather than the composite attribute as one field.
List Number | For a multivalued attribute, create a separate relation containing the owner's primary key and the multivalued value.
List Number | For a 1:1 relationship, place the primary key of one entity as a foreign key in the other, preferably where participation is total. Relationship attributes may be included there.
List Number | For a 1:N relationship, place the primary key of the 1-side as a foreign key in the N-side relation.
List Number | For an M:N relationship, create a separate relation containing the primary keys of both entities. These normally form a composite primary key.
List Number | For a weak entity, create a relation containing its attributes and the owner's primary key; the owner key plus the weak entity's partial key identifies the weak entity.
ExamText | Example: STUDENT(StudentID, Name) and COURSE(CourseID, Title) with ENROLLS(StudentID, CourseID, EnrollDate) represents an M:N relationship. StudentID and CourseID are foreign keys referencing their parent relations.
Normal | ER MODEL                         RELATIONAL MODEL
STUDENT ─── ENROLLS ─── COURSE   STUDENT(StudentID, Name)
   M             N                COURSE(CourseID, Title)
                                  ENROLLS(StudentID, CourseID,
                                          EnrollDate)

Heading 2 | 7. SQL — DDL, DML, DCL and TCL
ExamText | SQL is the standard language used to define and manipulate relational databases. It is declarative: the user specifies what result is required while the DBMS determines an execution strategy.
--- TABLE ---
Category | Purpose | Commands

Heading 3 | Important SQL clauses
ExamText | WHERE filters rows before grouping. GROUP BY forms groups. HAVING filters groups. ORDER BY sorts the result. JOIN combines rows from multiple relations. Aggregate functions such as COUNT, SUM, AVG, MIN and MAX summarize data.

Heading 2 | 8. Integrity and Referential Constraints
ExamText | Integrity constraints are rules that preserve correctness and consistency of database values.
List Bullet | Domain integrity: values must satisfy the data type/domain.
List Bullet | Entity integrity: primary-key values cannot be NULL and must uniquely identify tuples.
List Bullet | Referential integrity: a foreign key must refer to an existing referenced key or be NULL where permitted.
List Bullet | UNIQUE: prevents duplicate values in a constrained column/set.
List Bullet | CHECK: enforces a Boolean condition such as Salary > 0.
List Bullet | NOT NULL: prevents missing values where a value is mandatory.
ExamText | Example: FOREIGN KEY(CourseID) REFERENCES Course(CourseID) ensures that a student cannot reference a course that does not exist. Referential actions may include CASCADE, SET NULL, SET DEFAULT, or RESTRICT/NO ACTION depending on the DBMS and design.
Heading 3 | Why constraints matter
ExamText | Without constraints, invalid values can enter the database and cause application errors, inconsistent reports, broken relationships, and incorrect business decisions. Constraints move part of the correctness responsibility into the database itself.
Heading 2 | 9. Guidelines for Relational Schema Design
List Bullet | Each relation should have a clear and understandable meaning.
List Bullet | Avoid unnecessary redundancy.
List Bullet | Minimize NULL values where possible.
List Bullet | Use appropriate primary and candidate keys.
List Bullet | Represent relationships using foreign keys.
List Bullet | Normalize relations to reduce anomalies.
List Bullet | Choose appropriate data types and domains.
List Bullet | Enforce business-critical integrity rules at the database level.
List Bullet | Consider query performance and indexing after establishing a sound logical design.
List Bullet | Use controlled denormalization only when there is a justified performance or reporting requirement.

Heading 1 | UNIT 2 — NORMALIZATION, DATA STORAGE AND INDEXING
Heading 2 | 1. Functional Dependencies
ExamText | A functional dependency (FD) describes a relationship between attributes in a relation. X → Y means that whenever two tuples agree on all attributes of X, they must also agree on all attributes of Y. X is called the determinant and Y is functionally dependent on X.
ExamText | Example: StudentID → StudentName. If StudentID 101 identifies Ravi, every occurrence of StudentID 101 must have the same StudentName under this dependency.
Heading 3 | Why FDs matter
List Bullet | Identify candidate keys.
List Bullet | Detect redundancy.
List Bullet | Identify partial and transitive dependencies.
List Bullet | Guide normalization and decomposition.
List Bullet | Help prove whether a decomposition preserves important constraints.
Heading 3 | Important types
List Bullet | Trivial FD: Y ⊆ X.
List Bullet | Non-trivial FD: Y is not a subset of X.
List Bullet | Full dependency: Y depends on the whole determinant X.
List Bullet | Partial dependency: Y depends on only a proper subset of a composite key.
List Bullet | Transitive dependency: X → Y and Y → Z imply X → Z.
Heading 3 | Attribute closure
ExamText | The closure X+ is the set of all attributes functionally determined by X using a set of FDs. To compute X+, start with X and repeatedly add attributes that can be obtained from FDs whose left side is already contained in the closure. If X+ contains every attribute of the relation, X is a super key.
ExamText | Example: F = {A→B, B→C, C→D}. A+ starts as {A}; A→B gives B; B→C gives C; C→D gives D. Therefore A+ = {A,B,C,D}, so A is a key for this relation if these are all its attributes.
Heading 2 | 2. Normalization — Need and Goals
ExamText | Normalization is the systematic process of organizing relations using dependencies and decomposition so that redundancy and modification anomalies are reduced while important relationships and dependencies are preserved.
Normal | UNNORMALIZED DATA
      ↓ remove repeating groups / non-atomic values
1NF  ───────────────────────────────
      ↓ remove partial dependencies
2NF  ───────────────────────────────
      ↓ remove transitive dependencies
3NF  ───────────────────────────────
      ↓ every determinant must be a super key
BCNF ───────────────────────────────
      ↓ remove non-key multivalued dependencies
4NF  ───────────────────────────────
      ↓ remove problematic join dependencies
5NF / PJNF
ExamText | The goal is not to normalize blindly. A good design balances correctness, maintainability, query performance, and application requirements.
Heading 2 | 3. First Normal Form (1NF)
ExamText | A relation is in First Normal Form when each attribute contains atomic values and there are no repeating groups or nested sets stored inside a single relational field.
ExamText | Non-1NF example: STUDENT(StudentID, Name, Phones) where Phones contains '9876,8765'. A relational design stores one phone value per row in a separate relation.
ExamText | Decomposition: STUDENT(StudentID, Name) and STUDENT_PHONE(StudentID, Phone).
Heading 3 | Benefits of 1NF
List Bullet | Makes individual values addressable.
List Bullet | Simplifies searching and updating.
List Bullet | Removes repeating groups.
List Bullet | Provides a foundation for higher normal forms.
Heading 2 | 4. Second Normal Form (2NF)
ExamText | A relation is in 2NF if it is already in 1NF and every non-prime attribute is fully functionally dependent on the entire candidate key. Partial dependency is therefore the main problem addressed by 2NF.
ExamText | Example: ENROLL(StudentID, CourseID, StudentName, CourseName, Grade). Candidate key = (StudentID, CourseID). StudentName depends only on StudentID and CourseName depends only on CourseID. Therefore these are partial dependencies.
Normal | ENROLL(StudentID, CourseID, StudentName, CourseName, Grade)
          │             │
          │             └── CourseID → CourseName
          └──────────────── StudentID → StudentName

Decompose:
STUDENT(StudentID, StudentName)
COURSE(CourseID, CourseName)
ENROLL(StudentID, CourseID, Grade)
ExamText | The decomposition removes repeated student and course details and keeps Grade dependent on the complete enrollment key.
Heading 2 | 5. Third Normal Form (3NF)
ExamText | A relation is in 3NF if it is in 2NF and does not contain an undesirable transitive dependency of non-prime attributes on a key. Formally, for every non-trivial FD X → A, X is a super key or A is a prime attribute.
ExamText | Example: EMPLOYEE(EmpID, DeptID, DeptName). EmpID → DeptID and DeptID → DeptName. Therefore EmpID → DeptName transitively. DeptName should be moved to DEPARTMENT.
Normal | EMPLOYEE(EmpID, DeptID, DeptName)
      │
      ├── EmpID → DeptID
      │
      └── DeptID → DeptName
              ↓
       TRANSITIVE DEPENDENCY

EMPLOYEE(EmpID, DeptID)
DEPARTMENT(DeptID, DeptName)
Heading 2 | 6. Boyce-Codd Normal Form (BCNF)
ExamText | A relation is in BCNF if for every non-trivial functional dependency X → Y, X is a super key. BCNF is stricter than 3NF and removes certain redundancy that 3NF can allow.
ExamText | The key phrase to memorize is: 'Every determinant must be a super key.'
--- TABLE ---
3NF | BCNF
X→A allowed if X is super key OR A is prime. | X→Y allowed only if X is super key.
Less restrictive. | More restrictive.
Usually easier to preserve dependencies. | Dependency preservation may be lost.
Often practical compromise. | Used when stronger redundancy removal is required.
--- END TABLE ---
Heading 2 | 7. Multivalued Dependencies and 4NF
ExamText | A multivalued dependency X ↠ Y occurs when, for each value of X, the set of Y values is independent of the remaining attributes. It often arises when an entity has two independent multivalued properties.
ExamText | Example: STUDENT(Student, Hobby, Language). If a student's hobbies are independent of the languages the student knows, storing all combinations creates repeated combinations.
Normal | STUDENT
          /           \
       HOBBIES      LANGUAGES
         │              │
         └── independent ┘

Instead of one large relation:
STUDENT_HOBBY(Student, Hobby)
STUDENT_LANGUAGE(Student, Language)
ExamText | 4NF requires that every non-trivial multivalued dependency X ↠ Y has X as a super key.
Heading 2 | 8. Join Dependencies and 5NF
ExamText | A join dependency states that a relation can be reconstructed by joining several projections. 5NF, or Project-Join Normal Form, addresses redundancy that remains because of complex join dependencies not captured adequately by functional and multivalued dependencies.
ExamText | A relation is in 5NF when every non-trivial join dependency is implied by candidate keys. 5NF is relatively uncommon in routine application design but is important for understanding advanced relational decomposition.
ExamText | Exam distinction: 4NF deals with independent multivalued facts; 5NF deals with complex join dependencies and lossless reconstruction through projections.
Heading 2 | 9. Lossless Join Decomposition
ExamText | A decomposition is lossless if joining the decomposed relations produces exactly the original relation. It must neither lose valid information nor create spurious tuples.
ExamText | For binary decomposition R into R1 and R2, a standard FD-based condition is that the common attributes functionally determine all attributes of at least one side, under the relevant dependency set.
ExamText | Example: R(A,B,C), decomposed into R1(A,B) and R2(A,C). If A → B or A → C holds, the decomposition satisfies a common lossless-join criterion.
Normal | Original R(A,B,C)
       ↓ decomposition
 ┌────────────┐     ┌────────────┐
 │  R1(A,B)   │     │  R2(A,C)   │
 └──────┬─────┘     └──────┬─────┘
        └──────── JOIN ─────┘
                 ↓
          Original R recovered
Heading 2 | 10. Dependency Preservation
ExamText | A decomposition is dependency preserving if the important original functional dependencies can be enforced by enforcing dependencies on the decomposed relations individually, without requiring joins.
ExamText | Losslessness and dependency preservation are different properties. A decomposition may be lossless but not dependency preserving, or dependency preserving but not lossless. Good database design seeks both when possible.
--- TABLE ---
Property | Question it answers
Lossless join | Can I reconstruct the original relation exactly?
Dependency preservation | Can I enforce the original dependencies without joining decomposed relations?
--- END TABLE ---
Heading 2 | 11. Minimal Cover and Equivalence of FDs
ExamText | A minimal cover is an equivalent, simplified set of functional dependencies with no unnecessary attributes or dependencies.
Heading 3 | Steps
List Number | Split every FD so the right side contains a single attribute.
List Number | Remove extraneous attributes from left sides by testing whether they are unnecessary.
List Number | Remove redundant FDs if they can be derived from the remaining dependencies.
List Number | The resulting set is a minimal/canonical cover.
ExamText | Two sets F and G are equivalent when F+ = G+, meaning they imply exactly the same functional dependencies. Attribute closure is used to test implication.
Normal | EXAM-READY POINT: For numerical normalization questions, show every dependency, identify the candidate key, state the current normal form, identify the violation, decompose, and state why the new relations satisfy the target normal form.

Heading 2 | 13. B+ Tree Indexing
ExamText | A B+ tree is a balanced multiway search tree widely used for database indexing. Internal nodes contain separator keys and child pointers. Leaf nodes contain search keys and references to records/data pages. Leaf nodes are linked, which makes range scanning efficient.
Normal | [ 30 | 60 ]
                        /     |      \
                       /      |       \
              [10|20]      [40|50]    [70|80|90]
              / |  \        / | \       /  |  \
             ... ... ...    ... ... ... ... ... ...

Leaf level: [10,20] ↔ [40,50] ↔ [70,80,90]
                  linked for range traversal
Heading 3 | Search process
List Number | Start at root.
List Number | Compare search key with separator keys.
List Number | Follow the correct child pointer.
List Number | Continue until a leaf node is reached.
List Number | Search the leaf and follow the record/data pointer.
Heading 3 | Why B+ trees are efficient
List Bullet | Balanced height keeps search predictable.
List Bullet | High fan-out reduces tree height.
List Bullet | Linked leaves support efficient range queries.
List Bullet | Dynamic insertion/deletion maintains the tree structure.
List Bullet | Works well with disk pages because nodes can be sized to storage blocks.
ExamText | Complexity is typically O(log_f N) node visits where f is the fan-out, with the actual cost depending on page size, tree height, caching, and implementation.

 bucket 5
     ↓
 records / pointers

Heading 1 | UNIT 3 — TRANSACTION PROCESSING, CONCURRENCY CONTROL AND RECOVERY
Heading 2 | 1. Concept of a Transaction
ExamText | A transaction is a sequence of database operations that forms one logical unit of work. It may contain read, write, insert, update, delete, and control operations. A transaction must preserve database correctness even when several transactions execute concurrently or failures occur.
ExamText | Classic example: bank transfer. Transfer ₹500 from A to B requires subtracting ₹500 from A and adding ₹500 to B. If the system crashes after subtracting A but before adding B, the database becomes incorrect. Transaction management ensures that either both operations become permanent or both are undone.
Normal | BEGIN
  ↓
READ A → WRITE A
  ↓
READ B → WRITE B
  ↓
COMMIT ─────────→ changes permanent
  │
  └── failure ───→ ROLLBACK / RECOVERY
Heading 2 | 2. Transaction States and System Concepts
Normal | ACTIVE
                   │
             last statement
                   ↓
           PARTIALLY COMMITTED
              │           │

Heading 2 | 6. Lock-Based Concurrency Control and 2PL
ExamText | A lock is a concurrency-control mechanism that controls access to a data item. A shared lock S is used for reading and can be compatible with other shared locks. An exclusive lock X is used for writing and conflicts with both S and X locks.

Heading 3 | Two-Phase Locking
ExamText | Two-phase locking divides a transaction into a growing phase and shrinking phase. During the growing phase, the transaction may acquire locks but cannot release them. During the shrinking phase, it may release locks but cannot acquire new locks.
Normal | TIME →
┌──────────────────────┬─────────────────────┐
│ GROWING PHASE        │ SHRINKING PHASE     │

└──────────────────────┴─────────────────────┘
            LOCK POINT
       (last lock acquisition)
ExamText | Basic 2PL guarantees conflict serializability. Strict 2PL holds exclusive locks until commit/abort, reducing cascading rollback problems. Rigorous 2PL can hold both shared and exclusive locks until completion.

Normal | T1 holds A → waits for B
      ↑             ↓
T2 waits for A ← holds B
            CYCLE = DEADLOCK
List Bullet | Prevention: impose rules that prevent circular wait.
List Bullet | Avoidance: grant requests only when safe under the chosen protocol.
List Bullet | Detection: construct a wait-for graph and detect cycles.
List Bullet | Timeout: abort a transaction that waits too long.
Heading 2 | 7. Timestamp-Based Concurrency Control
ExamText | Timestamp ordering assigns every transaction a unique timestamp. Older transactions have smaller timestamps. The protocol ensures conflicting operations occur in timestamp order.
ExamText | For each data item X, Read_TS(X) stores the largest timestamp of a transaction that successfully read X, while Write_TS(X) stores the largest timestamp of a transaction that successfully wrote X.
ExamText | If a requested read or write would violate the timestamp ordering rules, the transaction may be rejected/aborted and restarted. A major advantage is that transactions do not wait for locks, so deadlocks due to lock waiting are avoided. A disadvantage is that repeated aborts can waste work.

Topic | Core sentence to remember
DBMS | A DBMS is software that provides facilities for defining, storing, retrieving, updating, securing and recovering data in a database.
Functional dependency | X → Y means that the value of X uniquely determines the value of Y.
1NF | A relation is in 1NF when attributes contain atomic values and repeating groups are removed.
2NF | A relation in 1NF is in 2NF when every non-prime attribute is fully dependent on the whole candidate key.
3NF | A relation is in 3NF when for every non-trivial X → A, X is a super key or A is a prime attribute.
BCNF | A relation is in BCNF when every determinant of a non-trivial functional dependency is a super key.
4NF | A relation is in 4NF when every non-trivial multivalued dependency has a super key as its determinant.
5NF | A relation is in 5NF when every non-trivial join dependency is implied by candidate keys.
Lossless join | A decomposition is lossless when joining its decomposed relations reconstructs exactly the original relation.
Transaction | A transaction is a logical unit of database work that must preserve correctness.
ACID | ACID stands for Atomicity, Consistency, Isolation and Durability.
Serializability | A schedule is serializable when its effect is equivalent to some serial execution of the transactions.
2PL | Two-phase locking has a growing phase for acquiring locks and a shrinking phase for releasing locks.
CAP | During a network partition, a distributed system cannot simultaneously guarantee both strong consistency and availability for every request under the CAP definitions.
Sharding | Sharding horizontally partitions data across multiple nodes.
NoSQL | NoSQL is a broad family of non-relational database technologies designed for flexible data models and scalable/distributed workloads.
Embedding | An embedding is a numerical vector representation of an object produced by an embedding model.
Vector similarity search | Vector similarity search retrieves stored vectors closest to a query vector according to a chosen similarity or distance measure.
Index | An index is an auxiliary access structure that improves data lookup performance at the cost of storage and maintenance.
